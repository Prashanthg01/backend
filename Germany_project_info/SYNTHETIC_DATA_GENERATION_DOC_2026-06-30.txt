1. WHAT IS SYNTHETIC DATA GENERATION AND WHY WE USE IT
────────────────────────────────────────────────────────────────────────────────

Synthetic data generation is the process of creating artificial data
programmatically, following statistical distributions and domain-specific rules,
so that the generated data resembles real production data structurally and
statistically — without being real data.

WHY WE NEED IT IN THIS PROJECT

  Real factory data (Frontpage.csv, Process.csv) is:
    - Confidential — cannot be shared across environments
    - Fixed — one snapshot, cannot test edge cases
    - Incomplete — may have missing products, zero-demand rows, etc.
    - Not reproducible — different every export

  Synthetic data solves all of these:
    - No confidentiality issues
    - Configurable — dial in any scenario (5 machines vs 3, 100 units vs 100,000)
    - Complete — every product has demand, every step has a machine
    - Reproducible — same seed always produces identical data
    - Stress-testable — push schedulers into bottleneck, overload, edge conditions

  We use it to test:
    - The ERT + MILP scheduler (Type 2)
    - The Shift-Aware scheduler (Type 1)
    - The comparative evaluation metrics
    - The Gantt chart and timeline visualisations
    - Batch optimisation ILP
    - Buffer optimisation LP

2. TECHNIQUE CLASSIFICATION
────────────────────────────────────────────────────────────────────────────────

The technique used in this generator is formally called:

  "Rule-Based Probabilistic Synthetic Instance Generation
   for the Job-Shop Scheduling Problem"

It is a sub-type of:

SPECIFIC TECHNIQUES USED INSIDE THE GENERATOR

  a) Seeded Pseudo-Random Number Generation (PRNG)
       Uses Python's random.Random class backed by the
       Mersenne Twister MT19937 algorithm (period 2^19937 - 1).
       A deterministic seed guarantees full reproducibility.

  b) Stratified / Tiered Sampling
       Demand is NOT drawn from a single uniform range.
       It is split into 3 demand tiers (low / mid / high) and
       weighted sampling chooses which tier applies to each product.
       This models real-world demand distributions where most products
       sell moderate volumes, few sell very little, and fewer still
       sell extremely high volumes — a right-skewed shape.

  c) Bernoulli Trials for Optional Steps
       Each optional routing step is added with a fixed probability p.
       This is a Bernoulli trial: rng.random() < p → include step.
       Results in routing depth variability across products.

  d) Uniform Continuous Sampling for Cycle Times
       Cycle time for each step is drawn from Uniform(a, b) where
       a and b are domain-constrained bounds per machine role.
       rng.uniform(a, b) maps to U[a, b].

  e) Categorical Sampling for Batch Sizes
       Batch size is drawn from a discrete categorical set
       {50, 100, 150, 200, 250} with equal probability.

  f) Proportional Role Partitioning for Machines
       Machines are divided into roles (cutting 30%, assembly 40%,
       molding 30%) deterministically from the total count n.
       This mirrors real factory resource allocation ratios.

  g) Scenario Parameterisation (Design of Experiments)
       The 4 named profiles implement a manual Design of Experiments
       (DoE) strategy — covering easy/hard/medium/variable test cases
       that bracket the expected real-world operating envelope.

  Library          Version    Role
  ───────────────  ─────────  ──────────────────────────────────────────────────
  Python random    stdlib     Mersenne Twister PRNG — seeded for reproducibility

    Machine           → name, available_hours_per_day
    Product           → item, sap_tn, sap_pl, dcc_type, description,
                        demand_2024, batch_size, num_batches
    ProcessStep       → product(FK), step_number, machine(FK), step_name,
                        cycle_time_seconds, workers_required
    ProductionSchedule → cleared before each fresh insertion

5. COMPLETE GENERATION PROCESS — STEP BY STEP
────────────────────────────────────────────────────────────────────────────────

  ══════════════════════════════════════════════════════
  STEP 5.1 — SEED AND RNG INITIALISATION
  ══════════════════════════════════════════════════════

  Entry: generate_synthetic_dataset(seed=42)

  Code:
    if seed is None:
        seed = int(time.time())   # non-reproducible fresh seed
    rng = random.Random(seed)     # isolated RNG instance

  Why an isolated instance?
    random.Random(seed) creates a private PRNG object separate from
    Python's global random state. This means:
      - Two calls with the same seed always produce identical data
      - The generator never interferes with any other random usage
        elsewhere in the Django/Celery codebase

  Machine count clamping:
    num_machines = min(num_products + 3, 15)   # auto-default
    num_machines = max(4, min(num_machines, 25))  # hard limits

  Hard limits rationale:
    min 4 machines — need at least 1 cutting + 1 assembly + 1 molding + 1 spare
    max 25 machines — scheduler complexity grows O(n²), cap prevents extreme runtimes

  ══════════════════════════════════════════════════════
  STEP 5.2 — MACHINE GENERATION  (_generate_machines)
  ══════════════════════════════════════════════════════

  Input : n (integer, total machine count)
  Output: list of dicts [ { name, available_hours_per_day, _role }, ... ]

  Role partitioning (deterministic, no randomness):

    n_cutting  = max(1, round(n × 0.30))
    n_molding  = max(1, round(n × 0.30))
    n_stations = max(1, n - n_cutting - n_molding)

  Example with n = 8:
    n_cutting  = round(8 × 0.30) = round(2.4) = 2
    n_molding  = round(8 × 0.30) = round(2.4) = 2
    n_stations = 8 - 2 - 2 = 4

  Machines are named sequentially: M1, M2, M3, ..., Mn
  They are assigned in this fixed order: cutting → assembly → molding

  Example with n = 8:
    M1 — cutting  — 24.0 h/day
    M2 — cutting  — 24.0 h/day
    M3 — assembly — 16.0 h/day
    M4 — assembly — 16.0 h/day
    M5 — assembly — 16.0 h/day
    M6 — assembly — 16.0 h/day
    M7 — molding  — 24.0 h/day
    M8 — molding  — 24.0 h/day

  Available hours rationale:
    Cutting  24 h/day  — automated, runs continuously (no operator needed overnight)
    Assembly 16 h/day  — operator-dependent, typically 2 shifts (8h × 2)
    Molding  24 h/day  — automated injection/overmolding press, runs overnight

  NOTE: Machine generation is DETERMINISTIC (no rng). Same n always gives
  same machine list. Only product demand and step assignment are random.

  ══════════════════════════════════════════════════════
  STEP 5.3 — DEMAND TIER SAMPLING  (_generate_products)
  ══════════════════════════════════════════════════════

  Demand distribution uses a 3-tier stratified model.

  DEFAULT TIERS (when no demand_range is given):
    Tier     Weight   Range
    low       20%     80  – 400
    mid       50%     400 – 1,500
    high      30%     1,500 – 4,500

  With a custom demand_range = (d_min, d_max), _scaled_demand_ranges() splits
  the range proportionally:

    span    = d_max − d_min
    low_top = d_min + int(span × 0.20)
    mid_top = d_min + int(span × 0.70)

    low  tier: [d_min,   low_top]
    mid  tier: [low_top, mid_top]
    high tier: [mid_top, d_max  ]

  Example with demand_range = (1000, 50000):
    span    = 49,000
    low_top = 1,000 + 9,800  = 10,800
    mid_top = 1,000 + 34,300 = 35,300

    low  tier: [1,000  – 10,800]  (20% of products)
    mid  tier: [10,800 – 35,300]  (50% of products)
    high tier: [35,300 – 50,000]  (30% of products)

  For each product i (1 to n):

    tier   = rng.choices(["low","mid","high"], weights=[0.2, 0.5, 0.3])[0]
    demand = rng.randint(tier_min, tier_max)

  rng.choices() performs weighted sampling without replacement for 1 draw.
  rng.randint(a, b) draws from the DISCRETE uniform distribution U{a..b}
  (both endpoints inclusive).

  The resulting demand distribution across products:
    - Is right-skewed (few high-volume products, many mid-volume)
    - Mirrors real Pareto-like production demand (80/20 rule approx.)
    - Is bounded — no extreme outliers beyond the user-specified range

  ADDITIONAL PRODUCT FIELDS:
    sap_tn      = f"TN-{rng.randint(100000, 999999)}"   always present
    sap_pl      = f"PL-{rng.randint(1000, 9999)}"       75% chance (rng.random() > 0.25)
                  or None                                25% chance
    dcc_type    = f"Type-{i}"                            deterministic by index
    description = f"P{i}"                                sequential label

  ══════════════════════════════════════════════════════
  STEP 5.4 — BATCH SIZE ASSIGNMENT
  ══════════════════════════════════════════════════════

  batch  = rng.choice([50, 100, 150, 200, 250])    uniform discrete sampling
  num_batches = max(1, round(demand / batch))

  Each of the 5 batch sizes has equal probability 1/5 = 20%.
  num_batches is the ceiling-rounded count of batches needed to cover demand.

  Example:
    demand = 1,250,   batch = 100   →  num_batches = round(12.5) = 13
    demand = 300,     batch = 250   →  num_batches = max(1, round(1.2)) = 1
    demand = 50,000,  batch = 200   →  num_batches = round(250) = 250

  ══════════════════════════════════════════════════════
  STEP 5.5 — ROUTING / PROCESS STEP GENERATION
  (_generate_process_steps)
  ══════════════════════════════════════════════════════

  This is the most complex part. For each product, a sequence of manufacturing
  steps is generated following a probabilistic precedence graph pattern.

  MACHINE POOL SETUP
    cutting_m  = [m["name"] for m in machines if m["_role"] == "cutting"]
    assembly_m = [m["name"] for m in machines if m["_role"] == "assembly"]
    molding_m  = [m["name"] for m in machines if m["_role"] == "molding"]

    Fallback (if any pool is empty due to rounding):
      cutting_m  → [machines[0]["name"]]
      assembly_m → [machines[min(1, len-1)]["name"]]
      molding_m  → [machines[-1]["name"]]

  TARGET DEPTH
    fixed mode   : avg_steps (user-supplied integer, same for all products)
    variable mode: rng.randint(3, 8) drawn independently per product

  STEP SEQUENCE — PROBABILISTIC ROUTING TEMPLATE
  ─────────────────────────────────────────────────
  Each "add(pool, time_range, workers)" call:
    1. Selects a machine: rng.choice(pool)         — uniform over pool
    2. Samples cycle time: rng.uniform(a, b)       — continuous U[a,b]
    3. Assigns a step number and "Step N" name
    4. Appends to product's step list

  Step  Type      Machine Pool   Probability  Cycle Time (sec/unit)  Workers
  ────  ────────  ─────────────  ───────────  ─────────────────────  ───────
   1    Cutting   cutting_m      100%         U[5.5, 9.5]            0.5
   2    Cutting   cutting_m      100%         U[5.0, 9.0]            0.5
   3    Assembly  assembly_m      65%         U[9.0, 20.0]           1.0
   4    Assembly  assembly_m     100%         U[7.0, 14.0]           1.0
   5    Assembly  assembly_m      30%         U[7.5, 13.0]           0.5
   6    Assembly  assembly_m     depth pad    U[8.0, 15.0]           1.0
   7    Test      assembly_m      50%         U[4.0, 8.0]            0.5
   8    Molding   molding_m      100%         U[13.0, 22.0]          1.0

  Step 6 "depth pad" fires when:  len(steps_so_far) < (target_depth - 1)
    This ensures products with few optional steps still approach the target depth.

  Result: each product has between 4 and 8 steps.
  Guaranteed minimum: steps 1, 2, 4, 8 always fire → minimum 4 steps.
  Maximum: all 7 optional/pad paths fire + steps 1,2,4,8 → 8 steps.

  EXPECTED STEP COUNT (analytical):
    E[steps] = 4 (mandatory) + 0.65 + 0.30 + P(depth_pad) + 0.50
             ≈ 4 + 0.65 + 0.30 + ~0.3 + 0.50
             ≈ 5.75 steps on average (variable mode)

  MACHINE SELECTION WITHIN POOL
    rng.choice(pool) draws uniformly at random from the pool.
    Different batches of the same product can land on different machines
    within the same role pool — this creates realistic machine sharing.

  ══════════════════════════════════════════════════════
  STEP 5.6 — PRIVATE FIELD STRIPPING AND OUTPUT ASSEMBLY
  ══════════════════════════════════════════════════════

  Internal _role fields on machines (and any future _ fields on products)
  are removed before output:

    clean_machines = [{k: v for k, v in m.items() if not k.startswith("_")} for m in machines]
    clean_products = [{k: v for k, v in p.items() if not k.startswith("_")} for p in products]

  Routing is flattened to a simple list of dicts:
    { item, machine, step, name, time, workers }

  Output dict:
    {
      "machines": [ { name, available_hours_per_day }, ... ],
      "products": [ { item, sap_tn, sap_pl, dcc_type, description,
                      demand_2024, batch_size, num_batches }, ... ],
      "routing":  [ { item, machine, step, name, time, workers }, ... ],
      "metadata": { dataset_type, num_products, num_machines,
                    steps_per_product, seed, demand_range,
                    total_routing_steps }
    }

  ══════════════════════════════════════════════════════
  STEP 5.7 — DATABASE INSERTION
  (insert_synthetic_dataset_into_db)
  ══════════════════════════════════════════════════════

  If clear_existing=True (default):
    DELETE all ProductionSchedule rows
    DELETE all ProcessStep rows
    DELETE all Product rows
    DELETE all Machine rows
    (in dependency order to respect FK constraints)

  Then INSERT in dependency order:
    1. Machine.objects.create(...)       for each machine
    2. Product.objects.create(...)       for each product
    3. ProcessStep.objects.create(...)   for each routing row
       (only if both product and machine FK lookups succeed)

  Returns:
    { products_created, machines_created, process_steps_created, metadata }

6. SCENARIO PROFILES — CONTROLLED TEST CASES
────────────────────────────────────────────────────────────────────────────────

  The SCENARIO_CATALOG defines 4 named test cases that bracket the realistic
  operating envelope. These implement a manual Design of Experiments (DoE).

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ Profile                        │ Products │ Machines │ Demand Range       │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ Low Demand / High Availability │    5     │    8     │   100 – 2,000      │
  │   seed 42 │ 3 steps            │          │          │                    │
  │   Purpose: baseline, easy, sanity-check                                  │
  │   Expected: avg util < 40%, no bottlenecks                               │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ High Demand / Bottleneck       │   20     │    3     │ 10,000 – 100,000   │
  │   seed 77 │ 6 steps            │          │          │                    │
  │   Purpose: stress test, MILP-critical paths, bottleneck machines         │
  │   Expected: avg util > 85%, long makespan                                │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ Capacity-Constrained           │   12     │    4     │  5,000 – 30,000    │
  │   seed 123 │ 5 steps           │          │          │                    │
  │   Purpose: medium load, test interleaving and gap elimination            │
  │   Expected: avg util 60–85%                                              │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ Variable Processing Time       │   10     │    6     │    500 – 50,000    │
  │   seed 999 │ 0 (random 3–8)    │          │          │                    │
  │   Purpose: heterogeneous mix, explore Gantt shapes                       │
  │   Expected: highly variable utilisation, unpredictable bottleneck        │
  └──────────────────────────────────────────────────────────────────────────┘

  WHY THESE 4?
  They deliberately exercise the 3 key scheduler failure modes:
    1. Underload  (Low Demand)    — verify no spurious overhead
    2. Overload   (High Demand)   — verify MILP kicks in and reduces makespan
    3. Contention (Constrained)   — verify gap elimination works
    4. Variability (Variable)     — verify scheduler handles heterogeneity

    Tier     Weight    Interpretation

  STEP PROBABILITY TABLE
    Step  Role      Always/Optional   Probability   Time Range (sec/unit)
    1     Cutting   Always            1.00          [5.5, 9.5]
    2     Cutting   Always            1.00          [5.0, 9.0]
    3     Assembly  Optional          0.65          [9.0, 20.0]
    4     Assembly  Always            1.00          [7.0, 14.0]
    5     Assembly  Optional          0.30          [7.5, 13.0]
    6     Assembly  Depth pad         conditional   [8.0, 15.0]
    7     Test      Optional          0.50          [4.0,  8.0]
    8     Molding   Always            1.00          [13.0, 22.0]

  WORKERS REQUIRED
    0.5   half-operator (shared across 2 stations)
    1.0   one full operator

  MACHINE ROLE PROPORTIONS
    Cutting  : 30% of machines → 24.0 h/day availability
    Assembly : 40% of machines → 16.0 h/day availability
    Molding  : 30% of machines → 24.0 h/day availability

  SAP_PL NULL RATE
    75% of products have a SAP_PL field.
    25% have null (sap_pl = None).
    Modelled as: rng.random() > 0.25 → assign value

8. FORMULAS USED
────────────────────────────────────────────────────────────────────────────────

  8.1 DEMAND TIER SPLIT
      span    = max(d_max − d_min, 3)
      low_top = d_min + max(1, floor(span × 0.20))
      mid_top = d_min + max(2, floor(span × 0.70))

  8.2 NUMBER OF BATCHES
      num_batches = max(1, round(demand_2024 / batch_size))

  8.3 MACHINE ROLE COUNTS
      n_cutting  = max(1, round(n × 0.30))
      n_molding  = max(1, round(n × 0.30))
      n_assembly = max(1, n − n_cutting − n_molding)

  8.4 AUTO MACHINE COUNT (when not specified)
      num_machines = min(num_products + 3, 15)
      num_machines = max(4, min(num_machines, 25))

  8.5 CYCLE TIME SAMPLING
      cycle_time_seconds = round(U[a, b], 2)
      where U[a, b] = rng.uniform(a, b)

  8.6 WEIGHTED TIER SELECTION
      P(tier = "low")  = 0.20
      P(tier = "mid")  = 0.50
      P(tier = "high") = 0.30
      sum = 1.00  ✓

  8.7 EXPECTED ROUTING DEPTH (variable mode)
      E[steps] = 4 (mandatory)
               + P(step 3) × 1   = 0.65
               + P(step 5) × 1   = 0.30
               + P(step 6) × 1   ≈ 0.30  (rough estimate, depth-dependent)
               + P(step 7) × 1   = 0.50
      E[steps] ≈ 5.75

10. EXAMPLE WALKTHROUGH — LOW DEMAND SCENARIO
────────────────────────────────────────────────────────────────────────────────

  Profile: "Low Demand / High Availability"
  Params : num_products=5, num_machines=8, steps=3, seed=42

  ── Machine Generation ──────────────────────────────────────────────────────
  n=8
    n_cutting  = round(8×0.30) = 2
    n_molding  = round(8×0.30) = 2
    n_assembly = 8 − 2 − 2    = 4

  Result:
    M1 cutting  24h   M2 cutting  24h
    M3 assembly 16h   M4 assembly 16h   M5 assembly 16h   M6 assembly 16h
    M7 molding  24h   M8 molding  24h

  ── RNG Init ─────────────────────────────────────────────────────────────────
  rng = random.Random(42)
  (Mersenne Twister seeded with 42 — deterministic from here)

  ── demand_range = (100, 2000) ────────────────────────────────────────────────
  span    = 1900
  low_top = 100 + int(1900×0.20) = 100 + 380 = 480
  mid_top = 100 + int(1900×0.70) = 100 + 1330 = 1430
  Tiers:
    low  : [100,  480]
    mid  : [480, 1430]
    high : [1430, 2000]

  ── Product P1 (i=1) ─────────────────────────────────────────────────────────
  rng.choices(["low","mid","high"], weights=[0.2,0.5,0.3]) → "mid"
  rng.randint(480, 1430) → 923   (demand_2024 = 923)
  rng.choice([50,100,150,200,250]) → 100   (batch_size = 100)
  num_batches = round(923/100) = 9

  sap_tn  = "TN-" + str(rng.randint(100000,999999))  → e.g. "TN-639427"
  sap_pl  → rng.random() = 0.71 > 0.25 → "PL-" + str(rng.randint(1000,9999))
  dcc_type = "Type-1"
  description = "P1"

  ── Process Steps for P1 (avg_steps=3, fixed mode) ───────────────────────────
  target_base = 3

  Step 1: machine = rng.choice(["M1","M2"]) → "M1"
          time    = rng.uniform(5.5, 9.5)   → 7.23 sec/unit
          name    = "Step 1", workers = 0.5

  Step 2: machine = rng.choice(["M1","M2"]) → "M2"
          time    = rng.uniform(5.0, 9.0)   → 6.81 sec/unit
          name    = "Step 2", workers = 0.5

  Step 3: rng.random() → 0.82 > 0.65 → SKIP (no optional assembly)

  Step 3: machine = rng.choice(["M3","M4","M5","M6"]) → "M4"
          time    = rng.uniform(7.0, 14.0)  → 10.44 sec/unit
          name    = "Step 3", workers = 1.0

  Step 4: rng.random() → 0.15 < 0.30 → ADD optional assembly
          machine = rng.choice([...]) → "M5"
          time    = rng.uniform(7.5, 13.0)  → 9.12 sec/unit
          name    = "Step 4", workers = 0.5

  Depth check: len(steps)=4 < target_base-1=2? NO → skip padding

  Step 5: rng.random() → 0.44 < 0.50 → ADD test step
          machine = rng.choice([...]) → "M3"
          time    = rng.uniform(4.0, 8.0)   → 5.91 sec/unit
          name    = "Step 5", workers = 0.5

  Final step: machine = rng.choice(["M7","M8"]) → "M8"
          time    = rng.uniform(13.0, 22.0) → 17.63 sec/unit
          name    = "Step 6", workers = 1.0

  P1 routing:
    Step 1 → M1 → 7.23 sec/unit
    Step 2 → M2 → 6.81 sec/unit
    Step 3 → M4 → 10.44 sec/unit
    Step 4 → M5 → 9.12 sec/unit
    Step 5 → M3 → 5.91 sec/unit
    Step 6 → M8 → 17.63 sec/unit
  (6 steps; nominal target was 3, but mandatory+optional steps drove it to 6)

  This same process repeats for P2, P3, P4, P5.

  ── Final Dataset Summary ─────────────────────────────────────────────────────
    machines list     : 8 entries
    products list     : 5 entries (P1..P5)
    routing list      : ~25-30 entries (5 products × ~5-6 steps each)
    metadata          : { dataset_type:"synthetic", seed:42, ... }

11. WHAT IS NOT MODELLED (KNOWN SIMPLIFICATIONS)
────────────────────────────────────────────────────────────────────────────────

  The following real-factory phenomena are intentionally excluded:

  a) SETUP TIMES
     No changeover/sequence-dependent setup times between different products
     on the same machine. In reality, switching product types often requires
     cleaning, retooling, or calibration.

  b) MACHINE BREAKDOWNS / MAINTENANCE
     Machines are assumed to be 100% available for their stated hours per day.
     No unplanned downtime, no preventive maintenance windows.

  c) WORKER SHIFT CONSTRAINTS
     Worker availability is modelled as a simple scalar (0.5 or 1.0).
     Actual worker scheduling (who, when, how many are available per shift)
     is not modelled.

  d) DUE DATES / DEADLINES
     Products do not have individual due dates. Demand is annual volume only.
     Priority scheduling based on urgency is not modelled.

  e) MATERIAL AVAILABILITY / LEAD TIMES
     All raw materials are assumed to be available at schedule start.
     No procurement delays or inventory constraints.

  f) PRODUCT FAMILIES / SEQUENCE DEPENDENCY
     Each product is treated independently. No grouping for efficiency,
     no "if product A just ran, starting product B is cheaper" logic.

  g) REWORK / SCRAP / QUALITY GATES
     All units are assumed to pass quality checks first time.
     No yield loss, no rework loops, no inspection hold times.

  h) ENERGY / CAPACITY COST MODELS
     No power consumption, no cost-per-hour per machine type modelling.

  i) REAL DEMAND SEASONALITY
     Demand is a single annual figure, not time-bucketed by month/quarter.

  j) MULTI-SITE ROUTING
     All products are produced within a single factory.
     No inter-site transport or outsourcing steps.

12. RELATED RESEARCH PAPERS AND REFERENCES
────────────────────────────────────────────────────────────────────────────────

  The methodology used here aligns with established academic practices for
  generating JSSP (Job-Shop Scheduling Problem) benchmark instances.

  ── FOUNDATIONAL JSSP BENCHMARK GENERATION ──────────────────────────────────

  [1] Fisher, H. & Thompson, G.L. (1963)
      "Probabilistic Learning Combinations of Local Job-Shop Scheduling Rules"
      In: Muth, J.F. & Thompson, G.L. (eds), Industrial Scheduling.
      Prentice-Hall, pp. 225–251.
      ► The original FT6, FT10, FT20 benchmark instances — generated using
        random uniform processing times on a fixed number of machines.
        Our cycle-time sampling directly follows this pattern.

  [2] Taillard, E. (1993)
      "Benchmarks for Basic Scheduling Problems"
      European Journal of Operational Research, 64(2), pp. 278–285.
      DOI: https://doi.org/10.1016/0377-2217(93)90182-M
      ► Taillard instances: jobs × machines grids with uniform random
        processing times. The standard benchmark suite for modern JSSP solvers.
        Our generator's uniform cycle-time ranges follow this convention.

  [3] Lawrence, S. (1984)
      "Resource Constrained Project Scheduling: An Experimental Investigation
       of Heuristic Scheduling Techniques"
      GSIA, Carnegie-Mellon University. Technical Report.
      ► LA01–LA40 instances. Introduced the idea of parameterising
        instance hardness by machine count and job count separately.

  [4] Demirkol, E., Mehta, S. & Uzsoy, R. (1998)
      "Benchmarks for Shop Scheduling Problems"
      European Journal of Operational Research, 109(1), pp. 137–141.
      DOI: https://doi.org/10.1016/S0377-2217(97)00019-2
      ► DMU instances. Extended Taillard methodology with structured
        variability in routing lengths — directly mirrors our optional-step
        Bernoulli trial approach.

  ── SYNTHETIC DATA GENERATION FOR MANUFACTURING ─────────────────────────────

  [5] Pinedo, M.L. (2016)
      "Scheduling: Theory, Algorithms, and Systems" (5th ed.)
      Springer.
      Chapter 2 covers probabilistic models for generating scheduling instances.
      ► Standard textbook reference for processing time distributions.

  [6] Blazewicz, J., Lenstra, J.K. & Rinnooy Kan, A.H.G. (1983)
      "Scheduling Subject to Resource Constraints: Classification and Complexity"
      Discrete Applied Mathematics, 5(1), pp. 11–24.
      DOI: https://doi.org/10.1016/0166-218X(83)90012-4
      ► Formal complexity classification of JSSP. Establishes why
        synthetic test instances are necessary (real data cannot cover
        worst-case complexity).

  ── TIERED/STRATIFIED DEMAND GENERATION ─────────────────────────────────────

  [7] Silver, E.A., Pyke, D.F. & Peterson, R. (1998)
      "Inventory Management and Production Planning and Scheduling" (3rd ed.)
      John Wiley & Sons.
      ► Chapter 3 discusses ABC analysis — the basis for our low/mid/high
        demand tier weights [0.2, 0.5, 0.3], which approximates a Pareto
        (80/20) demand distribution across a product portfolio.

  [8] Chopra, S. & Meindl, P. (2021)
      "Supply Chain Management: Strategy, Planning, and Operation" (7th ed.)
      Pearson.
      ► Chapter 13 on demand forecasting covers stratified demand modelling
        and why a uniform single distribution is unrealistic for production planning.

  ── REPRODUCIBLE SYNTHETIC DATA WITH SEEDED PRNG ────────────────────────────

  [9] L'Ecuyer, P. (1999)
      "Good Parameters and Implementations for Combined Multiple Recursive
       Random Number Generators"
      Operations Research, 47(1), pp. 159–164.
      DOI: https://doi.org/10.1287/opre.47.1.159
      ► Formal analysis of PRNG quality for simulation. Python's Mersenne
        Twister (MT19937) meets the criteria outlined here.

  [10] Matsumoto, M. & Nishimura, T. (1998)
       "Mersenne Twister: A 623-Dimensionally Equidistributed Uniform
        Pseudo-Random Number Generator"
       ACM TOMACS, 8(1), pp. 3–30.
       DOI: https://doi.org/10.1145/272991.272995
       ► The algorithm behind Python's random.Random. Period 2^19937 − 1,
         passes all Diehard tests. This is the PRNG our generator uses.

  ── DESIGN OF EXPERIMENTS FOR SCHEDULER TESTING ─────────────────────────────

  [11] Montgomery, D.C. (2017)
       "Design and Analysis of Experiments" (9th ed.)
       John Wiley & Sons.
       ► Chapter 2 on factorial designs — the 4 scenario profiles implement
         a 2-level manual design covering the (products × machines) space.

  [12] Watson, J-P., Barbulescu, L., Whitley, L.D. & Howe, A.E. (2002)
       "Contrasting Structured and Random Permutation Flow-shop Scheduling
        Problems: Search-Space Topology and Algorithm Performance"
       INFORMS Journal on Computing, 14(2), pp. 98–123.
       DOI: https://doi.org/10.1287/ijoc.14.2.98.120
       ► Demonstrates that the difficulty of scheduling instances depends
         critically on instance structure (our routing graph shape) not just
         raw size — motivating our structured routing template.
